<Prose>
  I built a 15-skill MCP that let 55 non-designers at Loop produce on-brand
  prototypes, email templates, slide decks, one-pagers, and marketing pages
  without waiting on me. I updated all 200+ of Loop's SendGrid email templates,
  and when the new ones went live, the CEO posted in Slack that customers were
  actually reading them for the first time. The MCP is deployed on the company
  GitHub and Vercel and is still in use after my internship ended.
</Prose>

<Spacer size="md" />

<Section id="first-attempt" title="The first attempt: pasting hex codes into Claude Code and getting pill buttons with the wrong font">
  <Prose>
    I started this project by accident. I was redesigning Loop's onboarding
    flow and needed to generate a screening page quickly. I opened Claude Code,
    gave it a few hex codes from the production site, and asked it to build an
    onboarding screen that would filter out restricted industries before
    applicants invested 20 minutes in a form.

    What came back was close enough to recognize as a fintech UI and far enough
    off to be unusable. The buttons had full pill rounding instead of the 8px
    radius we used. The font was a generic sans-serif, not DM Sans. The greens
    were approximately right but not the actual brand tokens. It was the AI
    version of "close enough," which in a regulated fintech means not close at
    all.

    That gap between "plausible" and "correct" is what made me realize I needed
    to build something more structured than a prompt.
  </Prose>
</Section>

<Section id="sandbox" title="Learning how agents work by building one from scratch in a VS Code sandbox">
  <Prose>
    I had never built an agent or written a skill before. I did not know how
    MCP worked. I started by researching: reading articles, watching talks,
    studying how other people structured agent workflows. But the thing that
    actually taught me was building one myself.

    I asked Claude Code to help me set up a sandbox experiment in VS Code. The
    idea was simple: I would write a screen spec, the agent would generate code
    from it, then the agent would check its own output and flag anything that
    did not match. Generate, compile, test, correct, repeat.

    The first version was rough. One early run reported success while writing
    an empty file because the script swallowed a malformed response. I fixed it
    to fail loudly and dump the raw response instead. Another run "passed"
    because the agent had quietly fallen back to native HTML elements instead
    of using Loop's real components. The green checkmark meant "it avoided the
    real components," which was the opposite of the goal.

    That was the moment I understood something important: a passing check is
    not proof of the thing you care about. You have to verify what passed, not
    just that something passed.

    I connected the agent to Loop's live Storybook component manifest (114 real
    components) and pointed it at the repo's AGENTS.md rules: semantic tokens
    only, real imports, no invented components. When the agent generated code
    now, it had to compile against the actual codebase, not a stand-in.

<Section id="skills" title="Fifteen skills, each with one job, grouped by who actually makes the request">
  <Prose>
    After I understood how to write and test a skill, I did not need the
    sandbox experiment anymore. Building the remaining 14 was a cycle of
    writing, testing, getting feedback, and refining. Each skill has one narrow
    job, one defined output, and one verification method.

    **Product UI (hard verification, type-checked against the real codebase):**
    generate-loop-ui produces Storybook stories from the real Next.js
    components. prototype-loop-ui generates sandbox prototypes for new flows,
    feature additions, or replicas of existing screens.
    reconcile-loop-design-system audits the gap between the Figma library and
    Storybook, producing a report plus Figma documentation updates.

    **Content and marketing (soft verification, human review):** loop-ui-copy
    generates labels, error messages, empty states, toasts, and accessibility
    labels with French counterparts, flagging anything that needs compliance
    review. loop-email-template produces email-safe inline-CSS HTML for
    SendGrid dynamic templates across four complexity tiers.
    loop-marketing-subpage generates clickable HTML prototypes for new pages on
    bankonloop.com. loop-brand-deck produces editable sales and marketing decks
    as .pptx files from 46 supporting brand assets. loop-one-pager creates
    editable one-pagers.

    I also built an ICP friction review skill that evaluates a flow from the
    perspective of Loop's ideal customer profile, and several more that I
    continued to add throughout the internship.

    The distinction between "hard" and "soft" verification mattered. The
    prototype skills compile and type-check against the real codebase. If they
    produce broken imports or invented components, the build fails. The content
    skills produce output for a human to review before anything goes live. No
    skill publishes anything directly to production.
  </Prose>
</Section>

<Section id="email" title="Updating 200+ email templates that nobody was reading">
  <Prose>
    Loop had over 200 email templates on SendGrid. They all technically worked,
    but nobody was reading them.

      before state with no information hierarchy, yellow divider lines, and raw

    - `Screenshot_2026-08-10_at_3_14_25_PM.png` — Old "You're Invited" email
      template with a dark green button that fills the full width and no visual
      structure
    - `Screenshot_2026-08-10_at_3_14_05_PM.png` — Old "Payment Complete" email
      template with yellow divider lines and no content hierarchy
    - `Screenshot_2026-08-10_at_3_13_46_PM.png` — Old "Your Plan Upgrade is
      Confirmed" email template with minimal styling and no brand hierarchy

    The templates had the Loop logo and the right dark green header, but the
    content was flat text with no hierarchy. Yellow and gold divider lines that
    did not match the brand. No clear CTAs. Fonts that fell back to system
    defaults. Some still referenced retired domains. Several showed raw
    Handlebars variables to the user.

    I built the email template skill (loop-email-template) around a block
    system: a base shell with Outlook/MSO conditionals, dark mode support, and a
    600px centered card, plus a set of composable partials (header, heading,
    paragraph, OTP code block, detail table, CTA button, feature card, footer).
    Every email type assembles from the same blocks, so they all look like one
    family.

    I wrote a strict rule into the skill: never invent amounts, codes, dates,
    offers, or legal copy. Those are either Handlebars variables filled by the
    sending system or approved text from the team. If something is missing,
    flag it. Do not fake it. Emails go to real customers.

    I updated all 200+ templates. Every one got the new block system, the
    correct brand green (#045b3f) CTAs, DM Sans typography, proper footers with
    the current address, and the retired domain links rewritten to
    bankonloop.com. Each template ships with a variables contract table mapping
    every Handlebars slot to its type and an example value.

<Section id="deployment" title="Deploying the MCP and teaching non-technical people to use it in a live demo">
  <Prose>
    I deployed the MCP to Loop's GitHub repo and to Vercel. Non-technical users
    connect through a bearer token in Claude Code.

    The entire engineering agentic system at Loop runs in Claude Code, so
    engineers were already comfortable in the terminal. For the non-technical
    team (CS, growth, sales, recruiting), I ran live demos. I sat with them,
    helped them set up their terminals, showed them how to open a project
    folder in Claude Code, and taught them prompt engineering techniques for
    getting better results from the skills.

    The gap between "here is how to install it" and "someone used it without
    me" was short. The CS team started generating docs with the skills within
    the same week. The engineering lead started using the deck generation skill
    to build pager duty workshops. Senior developers started using the
    prototype skill to push new features: savings account pages, business
    switcher flows, payment timeline roadmaps.

    The prototypes these skills produce are not production code. They are the
    starting point. A PM uses a prototype to show a client what a feature might
    look like. An engineer uses it as the visual target before writing the real
    implementation. The design system documentation baked into each skill (how
    to use each component, each token, each layout pattern) is what keeps the
    output close enough to production that the gap between prototype and
    shipped feature stays small.

<Section id="impact" title="What the MCP changed about how Loop operates">
  <Prose>
    Before the MCP, every branded asset was a synchronous request on me. Growth
    needed a pitch deck. Recruiting needed a styled job post. Engineering
    needed a quick mockup. CS needed an email template updated. All of it came
    through Slack, all of it waited in my queue.

    After the MCP, 55 people across engineering, growth, sales, and recruiting
    were self-serving branded work. My Slack stopped being the company's
    bottleneck for design output. I went from producing assets to producing the
    infrastructure that produces assets.

    The MCP also doubles as a design system diagnostic. When a skill tries to
    build a real screen and fails because a component is missing or a token
    defaults to black, that failure is a direct signal about what the design
    system still needs. The agent surfaced real gaps (missing typography
    components, missing layout primitives) just by trying to use the system. I
    would not have found those gaps as fast by hand.
  </Prose>
</Section>

<Section id="differently" title="What I would do differently">
  <Prose>
    **Ship fewer skills and measure which ones get used.** I built 15 skills
    before I had usage data on which requests were actually recurring. Some of
    the 15 are well-adopted. Some are still theoretical. If I started over, I
    would ship the prototype skill, the email skill, and the deck skill, watch
    what people actually use for a month, and expand from there.

    **Automate the email template QA pipeline.** Each template needs to be
    tested across Gmail, Outlook desktop, Outlook web, Apple Mail, and iOS. I
    did this manually for 200+ templates. A Litmus or Email on Acid integration
    inside the skill would have saved days.

    **Build the live MCP connection to Storybook.** The prototype skills
    currently work from an exported component manifest. A live connection to
    Storybook would mean the skills always reflect the current component
    library without a manual sync step. I documented this as the upgrade path
    for whoever picks it up next.
  </Prose>
</Section>

<Section id="lesson" title="The thing I learned that changed how I think about design tools">
  <Prose>
    I always thought of skills and MCPs as engineering tools. Something complex
    that requires deep technical knowledge to build. The sandbox experiment
    showed me they are not. A skill is a document that teaches an agent how to
    do one thing well. The hard part is not the technical structure. The hard
    part is knowing what "well" means for your specific context: which
    components are real, which tokens are current, which colors are forbidden,
    what the agent is not allowed to invent.

    That is design judgment applied to a new medium. The same instinct that
    tells you a button is too rounded or a font is wrong is the instinct that
    makes a skill produce correct output instead of plausible output.
    Distribution without taste is just more noise, faster.
  </Prose>
</Section>
