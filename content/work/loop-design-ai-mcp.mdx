<Section id="overview" title="A design MCP made of narrow contracts, not one general-purpose prompt">
  <Prose>
    This case study documents a Loop Financial Design AI MCP built from scratch
    as **12 separate skill definitions**. Each skill states when it should run,
    what evidence it must read, what it can produce, how it verifies the result,
    and where it must stop.

    The source package does not include usage analytics or adoption outcomes, so
    this case study does not claim them. The evidence is the system itself: 12
    skill contracts, a framework-free design-system export, its component
    preview, and an email-asset migration specification.
  </Prose>

<Section id="architecture" title="Twelve skills divide generation, review, product definition, and collateral">
  <Prose>
    The MCP's scope is visible in the frontmatter and rules of the 12 supplied
    skill files:

    - **loop-design-system** is the canonical reference to read before branded
      product work. It defines the source-of-truth hierarchy, tokens, component
      rules, responsive behavior, and known gaps.
    - **generate-loop-ui** turns a confirmed spec or rough idea into UI grounded
      in real Loop components, then type-checks and render-checks it.
    - **rebrand-to-loop** keeps an existing page's content and flow while
      replacing its visual layer with real Loop tokens and components.
    - **spec-loop-feature** turns an early feature idea into a review-gated spec
      and explicitly stops before product code is written.
    - **loop-screen-states** enumerates reachable loading, empty, error, pending,
      gated, and money-specific states from the data model.
    - **loop-design-qa** reviews a change against design-system and repository
      rules, with every finding tied to a real source.
    - **loop-ux-friction-review** walks a flow twice: first as a user, then as a
      senior UX reviewer.
    - **loop-compliance-review** reviews Canadian fintech artifacts and describes
      missing compliance features rather than only naming regulations.
    - **loop-ui-copy** produces product copy, next-intl keys, and French
      counterparts while escalating regulated language and unsourced numbers.
    - **loop-brand-deck** produces editable, token-grounded presentation decks
      and requires a render, correction, re-render, and token-verification loop.
    - **loop-marketing-subpage** creates review-ready HTML prototypes for the
      separate Webflow marketing system.
    - **loop-email-template** fills one frozen transactional-email layout and
      returns paste-ready SendGrid HTML plus its variables contract.

    The separation is intentional. Generation skills hand work to review skills;
    the feature-spec skill enforces a human confirmation gate; and the compliance
    and copy skills refuse to invent regulatory language, figures, rates, or
    timelines.
  </Prose>

  <PullQuote>
    The MCP is a routing system for evidence and constraints: each skill owns one
    job, one output, and a defined stopping point.
  </PullQuote>
</Section>

<Section id="truth" title="The architecture tells the agent where each kind of truth lives">
  <Prose>
    The core design-system skill distinguishes between two levels of evidence.
    Component states and token values come from the Loop Design System Figma
    file. Whole-page composition uses Figma and Storybook together: Storybook
    shows real composed screens and props, while Figma carries landmarks,
    heading hierarchy, focus order, container widths, and the grid contract.

    The supplied design-system skill records **528 variables across five
    collections**: 77 Primitives, 175 Semantic variables with light and dark
    modes, 229 Typography variables, 12 Effects, and 35 Layout variables. Its
    typography layer contains 40 mapped text styles. The chain is explicit:
    brand values feed aliases, aliases feed mapped implementation tokens, and
    components consume roles instead of raw hex values.

    This hierarchy is also a safety mechanism. Unreconciled Figma pages are not
    treated as Loop truth, missing components are flagged instead of fabricated,
    and disagreements between Figma and shipped code are reported rather than
    silently resolved.
  </Prose>
</Section>

<Section id="layers" title="One CSS export supports both the base surface and the application-flow treatment">
  <Prose>
    The supplied `loop-design-system.css` is a dependency-free export with
    tokens, typography, fields, buttons, surfaces, status patterns, app shell,
    motion, skeletons, dark-mode mappings, and responsive rules.

    It contains two treatments of the same components:

    - **Base** uses 10px radii, real 1px borders, and `brand-500` for primary
      actions. The README positions it for marketing, authentication, and
      sign-in surfaces.
    - **`.loop-app`** switches buttons to full pills, fields to 16px radii and
      16px text, borders to inset shadows, primary actions to `brand-600`, and
      section eyebrows to DM Mono. The same layer also works through `#app`.

    The layer is selected by wrapping a surface in `.loop-app`; omitting that
    wrapper keeps the base treatment. This preserves one component vocabulary
    while allowing the application flow to carry the V3.7 prototype's signature
    geometry.
  </Prose>
</Section>

<Section id="email" title="The email skill freezes the frame and lets only content and data vary">
  <Prose>
    The email skill defines one approved **Loop letter** rather than asking the
    model to design each message. Its frame is fixed: brand hero band, 600px
    white sheet, letter-style body, one pill CTA, and a standard footer. The
    documented body geometry includes `36px 48px 40px` sheet padding and a 20px
    gap between blocks.

    Requests arrive in plain language: purpose, audience, one action, changing
    data, transactional or marketing status, and sign-off. The skill then
    returns fully inline-CSS HTML for SendGrid, a variables table, suggested
    subject and preheader, a plain-text alternative, and every bracketed line
    that still needs approved copy. It does not send email or touch the live
    SendGrid account.

    There are customer and internal variants. Customer is the default. Internal
    is restricted to Loop staff alerts, monitoring, and reports; the supplied
    skill names a title instead of a greeting, no sign-off, and a reduced footer
    as visible differences. It says there are exactly four documented
    differences, but the referenced `LAYOUT.md` containing the complete list was
    not supplied, so the fourth is not inferred here.

    Both variants are light-mode only, table-based, and built with inline CSS.
    Customer emails have no body heading; the internal variant opens with a 24px
    title. One primary CTA is allowed, secondary actions are text links, and
    Outlook's square rendering of rounded elements is explicitly accepted.
  </Prose>
</Section>

<Section id="rehosting" title="The email migration treats old messages as an immutable archive">
  <Prose>
    A separate upload specification covers four images used across **183
    transactional email templates** and referenced **549 times**. The goal is to
    move them away from a personal Vercel project into the existing
    `loop-public` S3 bucket in `ca-central-1`.

    The four objects are:

    - `loop-email-hero-band.jpg` → `email/v1/hero-band.jpg`
    - `loop-email-hero-band-internal.jpg` →
      `email/v1/hero-band-internal.jpg`
    - `icon-website.png` → `email/v1/icon-website.png`
    - `icon-linkedin.png` → `email/v1/icon-linkedin.png`

    Email clients must be able to fetch them anonymously: no signed URLs,
    referer blocking, WAF gate, or rate limit. Every object needs
    `Cache-Control: public, max-age=31536000, immutable`.

    The versioned prefix is the archival constraint. A redesign publishes to
    `email/v2/` and leaves `email/v1/` untouched. Bucket versioning protects
    against data loss, but it does not protect an old email from changing when
    the same URL resolves to a newer object. Immutable keys do.

    The specification says one hero image is already at the bucket root without
    a cache header; the other three were not uploaded at the time of writing.
    After the final URLs exist, `bin/rehost-assets.py` is designed to verify HTTP
    200 responses before rewriting all templates and reshipping them to
    SendGrid. The source set does not include evidence that this migration ran.
  </Prose>
</Section>
