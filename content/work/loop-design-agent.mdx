<Section id="overview" title="Everyone at Loop needs a screen mocked up, and there is one designer.">
  <Prose>
    A sales rep needs a one-pager. An engineer needs a quick UI mock to argue
    about. A recruiter needs a job posting laid out. Each of these is a small
    ask and none of them is a good use of the only designer in the company.

    The obvious answer in 2026 is to point an LLM at it, and the obvious
    problem with that answer is that models generate UI code that looks right
    and does not work. They invent component names. They write markup that
    approximates your design system instead of importing it. Prompting harder
    does not fix this, because the model has no way to find out it was wrong.

    So the premise of this project is not a better prompt. It is a loop: the
    agent writes a screen, the machine checks it, failures go back in, and it
    tries again until it passes.
  </Prose>

  <Prose>
    Worth stating plainly, because it shaped everything about how this got
    built: I am a product designer, not an engineer. This project is also a
    record of learning the terminal, Node, git, and a production Next.js
    monorepo while building something real inside it.
  </Prose>
</Section>

<Section id="loop" title="Generate, compile, test, correct, and do not stop at the first green check.">
  <Prose>
    The harness is Node and TypeScript. A run goes:

    - **Generate.** The spec plus a selected component list goes to Claude,
      which returns React and TSX.
    - **Compile.** The output is built and type-checked against Loop's real
      repo, not a sandbox.
    - **Test.** A headless browser loads the resulting story in Storybook and
      checks whether it actually rendered or threw.
    - **Correct.** Any failure from either check, type error or runtime error,
      is fed back into the next attempt. Retries are capped, and the run fails
      loudly rather than quietly succeeding.

    The component vocabulary comes from Loop's live Storybook manifest, 114
    real components. The agent picks what a given screen needs and gets their
    real names, props and import paths, so it is composing Loop's library
    rather than describing something that resembles it. It is also pointed at
    the repo's own `AGENTS.md`, which spells out in CI-blocking detail what the
    codebase requires: semantic tokens only, the shared Button, real imports,
    no invented components.

    Storybook is the render surface for a specific reason. The production app
    sits behind an AWS Cognito auth wall that would have blocked automated
    rendering entirely, and Storybook renders the same components in isolation
    with no auth.
  </Prose>
</Section>

<Section id="checks" title="A passing check is not proof of the thing you care about.">
  <Prose>
    This is the lesson the project kept teaching, in both directions, and it
    is the reason the verification layer looks the way it does.

    An early run reported success while writing an empty file. The script had
    swallowed a malformed model response and treated the absence of an error as
    a result. Fixed by failing loudly and dumping the raw response.

    Later, the loop type-checked clean, and it was clean because the agent had
    quietly fallen back to native HTML instead of Loop's components. The green
    check meant "it avoided the real components", which is the precise opposite
    of the goal. I caught it by reading the agent's own flagged suggestions
    rather than its status.

    Then the reverse. The render check started failing on every attempt with
    the same error regardless of what code was generated, which is the
    signature of a broken harness rather than broken output. The screen was
    rendering fine in a browser. The detector was matching framework console
    noise through a selector that was too broad. Keying detection on
    Storybook's actual failure text fixed it.
  </Prose>

  <PullQuote>
    A check reporting failure is no more trustworthy than a green check
    reporting success. Verify what actually happened.
  </PullQuote>
</Section>

<Section id="boundary" title="The component that type-checked and still threw.">
  <Prose>
    The first time a generated screen rendered, the Button and the AlertBanner
    worked and the Select threw. `Cannot read properties of undefined (reading
    'id')`, deep inside react-aria-components' collection logic, on code that
    had type-checked clean.

    That is exactly the gap a type checker cannot close. The contract was
    valid and the runtime behavior was not, because Loop's Select is a compound
    React Aria component with a correct usage pattern that is not inferable
    from its type signature.

    Rather than write it up as a known limitation, I extended the loop across
    it in three layers. Detection: after type-check, drive a headless browser
    to the story's Storybook iframe and find out whether it rendered or threw.
    Feedback: route render errors into the same correction loop that already
    handled type errors, so a runtime failure is just another attempt.
    Grounding: hand the agent the repo's own `select.stories.tsx` as a worked
    example, so instead of guessing the React Aria pattern it copies the one
    Loop already uses.

    That third layer is what actually fixed it, and it fixed the type
    subtlety at the same time. The eligibility screen now generates with three
    working Selects, the real AlertBanner, the real Button and three branching
    states, type-checking and rendering verified by machine, on the first
    attempt of the final run.
  </Prose>
</Section>

<Section id="tradeoffs" title="What I chose, and what it cost.">
  <Prose>
    **Fetch to file over live MCP.** The agent reads a fetched copy of the
    component manifest rather than querying the Figma or Storybook MCP server
    live. Simpler, reliable, and the same data. The cost is that the manifest
    goes stale and someone has to refresh it, so live MCP is documented as the
    upgrade for whoever owns this next.

    **Invent but flag.** The agent builds only what the spec asks for. When it
    thinks something is missing, a restricted-industry gate on an eligibility
    screen for example, it surfaces that separately for a human instead of
    adding it. Good ideas stay visible without silently becoming the spec.

    **Type-check first, render-check second.** I shipped the check that catches
    the most failures before building the harder one. Which turned out to be
    the right order, since the render check is what exposed the Select problem
    and I would not have known to look for it earlier.

    **A branch and a scratch folder.** All of it runs in a clearly scoped
    location on a git branch so the agent cannot pollute the real repo. Not
    interesting, and the reason I could move fast inside a production codebase.
  </Prose>
</Section>

<Section id="diagnostic" title="It turned into a design system diagnostic by accident.">
  <Prose>
    Trying to build real screens out of Loop's real components surfaced gaps in
    the component library that nobody had catalogued: missing typography and
    layout primitives, tokens defaulting to black, components whose correct
    usage is not discoverable from their types. The agent found these by
    failing on them.

    That is the connection back to the reconciliation work. The design agent
    and the Figma to Storybook pipeline are one system rather than two: the
    pipeline is the infrastructure and the agent is what runs on top of it.
    Every gap the agent hits is a gap a human designer would have hit more
    slowly and reported less precisely.
  </Prose>
</Section>

<Section id="reflection" title="Reflection">
  <Prose>
    **Diagnosis discipline mattered more than building skill.** Almost every
    hour I lost went to a status that was lying to me in one direction or the
    other. The habit that got me through was refusing to trust a checkmark
    until I knew what it had actually checked.

    **Grounding beats prompting.** Every time the agent got something wrong, the
    fix was giving it Loop's real code rather than better instructions. The
    manifest, `AGENTS.md`, and eventually a worked example story. Prompt
    engineering was never the answer.

    **Build for the handoff you expect.** The bet was always that if this
    proved out, an engineer would own it. Knowing that from the start changed
    what I wrote down, and it is the reason the upgrade path is documented
    instead of just known by me.
  </Prose>
</Section>
